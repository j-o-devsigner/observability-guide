# Dynatrace as code (Monaco)

> **In 30 seconds:** SRE owns the **templates** (the baseline). Each service owns one short **`observability.yaml`**.
> `generate.py` turns every service file into Monaco configs (SLOs, custom alerts) and one routing workflow per team;
> one shared L1 dashboard serves all services through its `$service` variable. CI runs a dry run on every PR and
> `monaco deploy` on merge. Guide: [18](../standard/18-automation-and-scale.md).

## Layout

```text
dynatrace/
├── manifest.yaml              ← environments + projects; URLs and credentials from CI secrets
├── services-src/              ← one observability.yaml per service (in real life: in each service repo)
│   ├── checkout.yaml          ← archetype: api
│   ├── orders-worker.yaml     ← archetype: queue-consumer
│   └── nightly-billing.yaml   ← archetype: batch
├── templates/                 ← the baseline, owned by SRE ("one side")
│   ├── slo-availability.json · slo-latency.json · slo-queue-age.json
│   ├── alert-burn-rate.json · alert-client-ratio.json · alert-dlq.json · alert-batch-overdue.json
│   └── workflow-route-team.json
├── shared/                    ← deployed once
│   ├── config.yaml            ← document (kind: dashboard, private: false)
│   └── dashboard-service.json ← L1 dashboard with a $service variable
├── projects/                  ← GENERATED by generate.py, never edited by hand
│   ├── services/<service>/config.yaml
│   └── teams/<team>/config.yaml
├── generate.py                ← service files → Monaco configs
└── check.py                   ← offline check: templates exist, parameters provided, rendered JSON valid
```

## What each archetype gets

| Archetype | Configs generated | Monaco type |
|---|---|---|
| `api` | Availability SLO, latency SLO (if `latency_ms`), fast-burn alert, per-client error-ratio alert (if `per_client`) | `slo-v2`, `settings` (`builtin:davis.anomaly-detectors`) |
| `queue-consumer` | Oldest-message-age SLO, DLQ count alert, backlog-growing-at-max-consumers alert (if `max_consumers`) | `slo-v2`, `settings` |
| `batch` | "No successful run in 2 intervals" alert | `settings` |
| `platform-service` | Internal SLO from callers' client spans (`server.address`), one saturation alert per listed resource (e.g. connections) | `slo-v2`, `settings` |
| every team | Workflow: problems with `team = <team>` → the team's on-call channel | `automation` (`workflow`) |
| everyone | One L1 service dashboard | `document` (`dashboard`) |

Alerts set `team` and `runbook` on the event they raise, so the team's Workflow can route them and the page carries the runbook.

## Pipeline

| Step | Command | When |
|---|---|---|
| Generate | `python3 dynatrace/generate.py` | PR and merge (fails if a service file misses `service`, `team`, `tier`, `archetype` or `runbook`) |
| Offline check | `python3 dynatrace/check.py` | PR |
| Dry run against the tenant | `monaco deploy dynatrace/manifest.yaml --dry-run` | PR |
| Deploy | `monaco deploy dynatrace/manifest.yaml` | Merge to main |
| Remove a retired service | Delete its service file and run `monaco delete` with a delete file listing its config IDs | When a service is decommissioned |

Credentials (CI secrets): `DT_ENV_URL`, `DT_API_TOKEN` (settings), `DT_OAUTH_CLIENT_ID` / `DT_OAUTH_CLIENT_SECRET` (SLOs, documents, workflows), with only the scopes those configs need.

## Rules

| Rule | Why |
|---|---|
| **Config IDs include the service or team name** | Monaco identifies objects by ID; a shared ID would make each service overwrite the last |
| **Bootstrap templates with `monaco download`**: build one SLO, alert, dashboard and workflow in the UI for a pilot service, download, then replace values with `{{ .param }}` | The JSON schema is the tenant's, not a guess; the templates here are shapes to show the idea |
| Keep templates simple: parameters only, no logic | Monaco docs advise it; logic belongs in `generate.py` |
| Escape workflow expressions as `{{ "{{" }} … {{ "}}" }}` | Workflows use `{{ }}` too; Monaco would try to fill them |
| Documents created by Monaco are private unless `private: false` | Otherwise only the deploying identity sees the dashboard |
| Nobody edits generated objects in the UI | The next deploy overwrites them; change the template or the service file |
| Thresholds are tier defaults in `generate.py`; a service can override them in its file | One place for defaults, explicit exceptions |
